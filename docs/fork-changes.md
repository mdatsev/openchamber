## Prime New-Root Boundary

Prime new-root creation is available only as an explicit OpenChamber server POST that sends one daemon create and one initial prompt on the same connection. It has no automatic retry or HTTP idempotency: any transport/protocol uncertainty reports that creation may have succeeded and directs the client to refresh the catalog before another explicit attempt. Do not add heuristic reconciliation, cleanup of an uncertain root, or the discarded export/copy workaround. The shared draft selector/client sends exactly `{ workingDirectory, message }` by default. A locally customized model/thinking selection is sourced only from a fresh retained Prime snapshot and adds an exact public source fence plus model pair and, only for the source current model, optional thinking. The client passively refreshes and revalidates that source immediately before POST; the server rechecks its current cached authority immediately before the single daemon create write. Missing or stale configuration fails before creation without downgrading, while an unconfigured request preserves Prime defaults. Every unconfigured Prime draft exposes Load Prime options. Only that direct user action passively refreshes the catalog, chooses an adapter-private ready source by same draft working directory and then latest update, and explicitly activates the exact winner without changing visible selection; draft opening and render remain passive. Protocol v7/schema 13 has no pre-session model catalog, so an authoritative absence keeps the action retriable and explains that options require an existing Prime session. Working directory and source/configuration stay in bounded full-draft-keyed adapter-private state, changed or uncertain captured text is preserved, and an accepted root activates only after refreshing the Prime catalog.

## Maintenance

- Record every fork-only source, configuration, build, or user-visible behavior change when it is introduced. Keep related edits that implement one capability in one entry.
- Keep entries concise and current. Record owning paths and an upstream issue or pull request when one is known.
- This is an active divergence index, not a changelog. Do not record upstream-only changes, routine synchronization merges, temporary work, generated output, or policy-only documentation.
- Remove an entry when its fork implementation has been removed. Git history preserves the previous record.
- Before integrating an upstream release, compare its changes with every active entry.
- When upstream provides the same fix or behavior, remove the fork implementation, use the upstream implementation, validate the affected behavior, and remove the entry.
- When upstream provides similar but different behavior, changes the same owning area, or leaves equivalence uncertain, stop the integration and ask the user how to proceed.
- Do not retain redundant fork code as a compatibility layer after an equivalent upstream implementation is adopted.
