# Incident: OpenChamber OOM kill left stale turns

- **Type:** record
- **Purpose:** Record why multiple OpenChamber sessions stopped progressing without showing their unexpected-interruption state.
- **When to read:** When sessions retain unfinished assistant turns or running tools after the managed OpenCode server restarts, especially following system memory pressure.

## Resolution (TL;DR)

On 2026-08-11, `systemd-oomd` killed the official `openchamber.service` cgroup after it reached 8.3 GB peak memory while several sessions and memory-heavy validation commands were active. Systemd restarted OpenChamber six seconds later, but the killed requests could not resume and six assistant turns remained unfinished in the shared OpenCode database. The UI's interruption classifier also returned early for reconciled explicit idle state; preserving authoritative snapshot active-set membership fixes that presentation gap. Affected sessions must still be resumed with a new prompt, preferably one at a time after inspecting partial work.

## Status

workaround

## Desired recovery topology

The user clarified that the goal is development continuity rather than multiple equivalent OpenChamber control planes: a custom development instance must be restartable or allowed to break while long-running OpenCode sessions continue, and the regular OpenChamber must be able to reconnect to and continue those same sessions. The selected first-stage design is one stable external OpenCode runtime and exactly one active OpenChamber surface, with an independent switch command replacing regular and custom surfaces without stopping OpenCode. OpenChamber-owned automation continuity and external plugin provisioning remain separate follow-up boundaries.

## Timeline + investigation

- At 2026-08-11 21:10:36 EEST, the user systemd journal recorded `systemd-oomd killed 30 process(es) in this unit` for `openchamber.service`. The unit reported an 8.3 GB memory peak and 338.3 MB swap peak.
- The pre-kill OpenCode log showed several concurrent sessions and, immediately before the kill, parallel UI/web type checks, lints, focused tests, and documentation checks. Other long-lived OpenChamber and development server instances increased the machine's baseline memory use, but the journal identifies memory pressure and the selected official service cgroup as the terminating event.
- Systemd restarted `openchamber.service` at 21:10:42. Its managed OpenCode server became ready on port `46361` by 21:10:45, and `http://127.0.0.1:8792/health` subsequently reported both OpenChamber and OpenCode healthy.
- The shared `~/.local/share/opencode/opencode.db` remained readable. A read-only query found six assistant messages created before the kill without `time.completed`; three retained tool parts recorded as `running`. The live `/session/status` authority after restart correctly omitted those dead requests, so they were idle rather than active and could not make further progress.
- The affected top-level sessions included `Restart openchamber CUSTOM only`, `Debugging duplicated conversation responses`, `Simplifier agent session impact analysis`, `YouTube extension mobile UI fixes`, and `OpenChamber custom settings and restart button`; the latter also owned an unfinished explore subagent.
- The fork's unexpected-interruption behavior compared an unfinished message with a successful snapshot timestamp, but `useSessionActivity` returned idle before that check whenever the directory store contained an explicit idle status. Authoritative reconciliation writes exactly that idle state when an earlier busy session is absent from a snapshot, suppressing the warning in this restart path.
- The UI fix retains the active IDs from each successful authoritative status snapshot. An unfinished turn is interrupted only when it predates a snapshot that omitted it, independent of cached idle representation. A snapshot that included the session remains distinguishable from a later ordinary idle event, avoiding false interruption during normal message-completion races.
- Operational recovery is to inspect each affected worktree and send a new continuation prompt. In-flight shell commands may have completed partially before the cgroup kill, so recovery must not assume success or blindly rerun destructive operations. Resume memory-heavy sessions sequentially on this 16 GB host.
- Follow-up prevention research against OpenCode 1.18.10 confirmed that `tool.execute.before` may mutate bash arguments, but OpenCode runs its command parser and permission checks after that hook. A plugin that rewrites `command` to a `systemd-run` invocation would therefore make permission rules and prompts describe the wrapper rather than the model-requested command.
- OpenCode's `shell` configuration is a safer no-upstream-change boundary. A plugin config hook can select an executable shell launcher while leaving the tool argument unchanged; the launcher can `exec systemd-run --user --scope` around the real non-interactive shell. OpenCode then parses and approves the original command, while its existing working-directory, output capture, timeout, and process-group cancellation remain outside the launcher boundary.
- Live shell-tool probes successfully created transient scopes with `MemoryAccounting=yes`, `MemoryMax=64M`, `MemorySwapMax=0`, and `OOMPolicy=kill`, preserving the working directory and combined stdout/stderr. OpenCode's one-second timeout killed a scoped sleep without leaving a unit or process behind. A 256 MB allocation was OOM-killed inside its 64 MB scope immediately and both OpenChamber services survived, but `systemd-run --scope --collect` did not return to OpenCode until the outer 120-second tool timeout. The naive wrapper is therefore unsuitable for rollout: a launcher must avoid or independently resolve that systemd 255 failure-path hang, and actual limits still need validation.
- A follow-up probe explained the apparent failure-path inconsistency: with `MemoryHigh=32M` and `MemoryMax=64M`, the allocator remained throttled near 34 MB for more than ten seconds with `MemoryAvailable=0`, never reached the hard limit, and emitted no OOM result. Setting the soft and hard limits equal produced an immediate kill. The runtime therefore omits lower `MemoryHigh` thresholds and supervises blocking `systemd-run --scope` without `--collect`; the hard `MemoryMax` boundary returns promptly, while the supervisor propagates exit status, handles cancellation, and clears the failed transient unit.
- Per-command `MemoryMax` contains one pathological command. An aggregate tools slice can protect the OpenCode service from concurrent aggregate pressure, but exhausting that parent may kill more than one command scope; this trade-off must remain explicit rather than being presented as strict per-command isolation.
- Separating OpenCode from OpenChamber also requires external plugin provisioning to retain the OpenChamber agent tool and optional system-prompt optimizer. The minimal secure local design is a single designated OpenChamber control owner, a stable plugin loaded by external OpenCode, and an atomically replaced mode-0600 connection file that the tool reads for each call. This lets the owner rotate its loopback endpoint token after an OpenChamber restart without restarting OpenCode. It does not solve remote-host injection or multiple competing OpenChamber owners.
- Multiple OpenChamber instances may safely observe one OpenCode only when OpenChamber-owned side effects have a single owner. Every server process starts its own scheduled-task runtime, whose timers, queue, running set, and concurrency guards are process-local; two instances loading the same project task definitions can dispatch the same scheduled task twice. Settings and project-config writes are atomically replaced but serialized only by process-local promises, so instances sharing the default `~/.config/openchamber` files can also lose concurrent read-modify-write updates. Agent-tool endpoint/token ownership, OpenCode restart/configuration, notifications, tunnels, and permission responses have the same single-owner or explicit-coordination requirement.

Evidence sources: `journalctl --user -u openchamber.service`, `systemctl --user status/show openchamber.service`, `oomctl`, `http://127.0.0.1:8792/health`, `~/.local/share/opencode/log/opencode.log`, and read-only queries against `~/.local/share/opencode/opencode.db`.
